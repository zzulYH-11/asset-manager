# Decision Log

이 문서는 프로젝트 진행 과정에서 발생한 핵심적인 기술적 의사 결정(Architecture & Technical Decisions)의 배경과 대안, 그리고 그 결과를 누적 기록하는 공간입니다.

---

## 2026-06-30

### 결정

* 프런트엔드 기술 스택을 순수 웹 기술(Vanilla HTML/CSS/JS)에서 **React(v19) + Vite(v8)** 기반으로 마이그레이션(리빌딩).
* 포트폴리오 시각화를 위해 **Chart.js** 및 **react-chartjs-2** 도입.

### 이유

* **상태 관리의 효율성**: 자산 관리 서비스의 특성상 포트폴리오 추가/삭제, 대시보드 갱신, 시장 지표 변동 등 동적 상태 관리가 핵심입니다. React의 선언적 UI 구조는 이러한 복잡한 동적 렌더링을 일관되게 통제할 수 있습니다.
* **컴포넌트 재사용 및 유지보수성**: UI를 컴포넌트 단위로 구조화함으로써 코드가 스파게티화되는 것을 방지하고, 에이전트(AI)가 프런트엔드를 완결성 있게 책임지고 고품질로 개선하기에 훨씬 안정적입니다.
* **강력한 생태계**: 차트 시각화 및 아이콘 시스템 등을 구현할 때 검증된 라이브러리(Chart.js, Font Awesome)를 안정적으로 통합하기 위해 현대적인 패키지 매니저(NPM) 생태계가 필수적입니다.

### 대안

* **기존 순수 웹 기술(Vanilla JS) 유지**: 빌드 환경 구성이 필요 없다는 장점이 있으나, 향후 서비스 확장 시 복잡해지는 DOM 조작 및 상태 불일치 문제를 해결하기 위한 비용이 프레임워크 도입 비용보다 훨씬 클 것으로 판단했습니다.

### 결과

* `npx create-vite`를 통해 `frontend/` 디렉토리에 React 개발 환경이 성공적으로 구축되었습니다.
* 기존 HTML/CSS 기반의 프리미엄 디자인(글래스모피즘 및 다크모드)이 React 컴포넌트(`App.jsx`, `index.css`)로 이식되었습니다.
* 로컬 상태 및 LocalStorage를 연동한 자산 추가/삭제 기능(CRUD), Chart.js 기반의 실시간 포트폴리오 비율 시각화 기능이 모두 복구되어 정상 동작합니다.

## 2026-06-30

### 결정

* **MVP 스펙 정합을 위한 API 간소화 및 로그인 보류**
* 사용자 구분을 위한 **경량 무인가 헤더(`X-Member-Id`)** 설계 도입.

### 이유

* **MVP 개발 속도 극대화**: `docs/02-mvp.md`에 명시된 "회원가입/로그인 제외" 규칙에 맞추어 연동 비용과 보안 설정을 최소화하고, 서비스 핵심인 '미국 주식 및 지표 관리' 기능의 빠른 배포에 집중하기 위함입니다.
* **최소한의 멀티유저 식별 보장**: 회원가입은 없애되 추후 v2 확장 시 데이터베이스 마이그레이션이 용이하도록, HTTP 요청 헤더에 사용자 고유 아이디(`X-Member-Id`)를 탑재하여 백엔드에서 소유주를 최소 식별할 수 있도록 타협점을 설계했습니다.

### 대안

* **풀 스택 Spring Security & JWT 구현**: 인증의 완성도는 높으나 프런트-백엔드 간의 OAuth2, 토큰 갱신 등 연동 범위가 과해져 MVP 배포 일정이 크게 늘어질 우려가 있었습니다.

### 결과

* 로그인/회원가입 관련 API 명세 및 컨트롤러 구성을 비활성화(주석 처리)하고, 단순 자산 목록 CRUD용 API 스펙으로 간소화했습니다.
* 프런트엔드는 임시 회원 ID `1`을 헤더에 실어 통신하며, 백엔드는 해당 ID를 바탕으로 데이터를 안전하게 필터링하여 응답합니다.

## 2026-07-01

### 결정

* **프런트엔드 API 호출 경로 리팩토링 (호스트와 경로의 명시적 분리)**
* `API_BASE`에서 `/api`를 떼어내고, 요청 시점에 `/api/stocks` 형태로 붙이도록 수정.

### 이유

* **Vercel 환경 변수 설정의 편의성**: Vercel에 환경 변수를 입력할 때 끝에 `/api`가 빠지면 통신이 깨지는 문제를 미연에 방지하여, 사용자가 순수 호스트 주소(도메인)만 기입해도 정상 동작하도록 하기 위함입니다.
* **장기적인 API 버전 관리 및 라우팅 유연성**: 나중에 `/api`가 아닌 외부 서비스 연동 경로(예: `/api2`, `/v2`, `/auth` 등)로 개별 API를 유연하게 쏠 수 있도록 API Base와 개별 요청 경로의 밀결합을 해제했습니다.

### 대안

* **기존 결합 구조 유지**: 간편하지만, 백엔드가 다중 버전을 서비스하거나 프런트가 제3의 외부 API를 연동해야 할 때 주소 분리가 매우 지저분해지는 한계가 있습니다.

### 결과

* `App.jsx`에서 `API_BASE`를 `import.meta.env.VITE_API_URL` (순수 도메인 주소)로 재설정하고, 개별 `fetch` 구문에서 `/api/stocks` 등의 패스를 직접 선언했습니다. Vercel 배포 시 `https://[주소]` 형태만 입력하면 즉시 통신이 완료됩니다.
